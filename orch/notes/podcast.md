## podcast-stop (PR #71, 34593eab) — notes for the next story of this track
- libVLC 4's Java `EndReached` is libvlc_MediaPlayerStopping: it comes at a natural end, after every EncounteredError and on a drop. After it `PlayerController.playbackState` stays PLAYING (stale `service.isPlaying`), progress keeps the last time; after an error progress is (0, 0) and the state STOPPED.
- `ResumeHook.dropout: DropoutGuard` (vlc-android media): `PlaylistManager` asks it on EndReached/EncounteredError (`droppedStream`), calls `stopped()` in `stop()`, and `reopenCurrent(ms)` reopens via the S-1302 `CastResume` path. `recovering` keeps the foreground and the Wi-Fi lock; pause/play while waiting set `dropoutPaused` (opens paused).
- `ResumeHook.halted/haltStamp(location)`: a counter per location of ends/errors/stops; `EpisodeControl.haltStamp` and `StartWait` (podcast) use it.
- Pure rules: `app.nagmedar.ui.playback.StreamDropout` (verdict), `PlaybackRules` now lives in `app.nagmedar.ui.playback` (RESUME_END_THRESHOLD_MS = 5 s).
- `DropoutRecovery` (podcast) is created by `PodcastPlaybackObserver.attach`, fed by its look loop; `EpisodeTracker.reopened()` freezes saves until it plays again.
- `StreamWifiLock` (vlc-android util) held by `PlaybackService.updateWifiLock()`.
- `--http-reconnect` only exists in VLC 4's legacy http module (priority 0) — useless; radio streams have no app-level reconnect yet.

## radio-reconnect (PR #73, 8e4b56bb) — notes for the next story of this track
- One guard for everything: `DropoutRecovery` (still in podcast/, driven by PodcastPlaybackObserver's look loop for ANY media) handles episodes and live streams. Live = http(s), no episode context, no length (`StreamDropout.verdict(..., episode = false)`, duration <= 0): reconnect `Reopen(0, …)` via `reopenCurrent(0)`; never-played (seenMs/time 0, retries 0) → End so .pls/.m3u expansion (done in the playlist's EndReached handler) still works; a clean end at the same place (≥10 s) as the last one → End (lengthless file). Non-episode with a length → End (not handled, as before). Notice `nag_live_dropout_gave_up`.
- `StreamStall` (playback/StreamDropout.kt): armed once the time moved; 20 s or 2× KEY_NETWORK_CACHING_VALUE. On a stall the guard computes the verdict with error=true, then `PlaylistManager.dropStalled()` (mediaplayer.stop(); its Stopping/EndReached is swallowed by the pending reopen) and `reopen()`.
- `PlaylistManager.droppedStream`: a drop while PlayerController is PAUSED sets `dropoutPaused` (opens paused).
- No connecting/buffering state exists in the player bar; none added. Recordings (RecordingSession) already retry (5 failures, backoff 1–16 s, 25 s read timeout) but do not wait for a network: an outage > ~30 s ends a recording as Failed (with its notification).
- Possible false stall: a stream whose libVLC time freezes while audio plays (broken timestamps) would reconnect every 20 s; not seen, device check.
- Follow-up c268c303: StreamStall progress = time moved OR libVLC --stats counters grew (`StreamCounters`: readBytes, demuxReadBytes, playedAbuffers via `PlaylistManager.currentStats()`, media released after). No counters (null/all 0): time only, live ≥ 45 s (`BLIND_LIVE_MS`). The "time frozen while audio plays" false stall is closed.

## playback-fixes (story/playback-fixes, review-1.0-playback fixes) — notes for the next story of this track
- Dropout states: `DropoutGuard.reopenPending` (libVLC stopped, not opened yet) vs `recovering` (the service's hold: pending, or opened and not playing on yet; false while paused once opened). `DropoutHold` (vlc-android media, `PlaylistManager.dropoutHold`) is the playlist side: while pending the player is PLAYING or PAUSED as it was (`PlayerController.beforeError` keeps the state/place an EncounteredError resets), so focus loss, the noisy receiver, SleepTimer and the buttons all act on it; play()/pause() use `reopenPending()` only; `left()` on any playIndex that is not the reopen's; `opening()` gives the CastResume's paused flag.
- `DropoutRecovery(host: DropoutHost, scope, reopened)`; `ServiceDropoutHost` adapts PlaybackService. Given up while paused it parks (still pending, no job, waiting false, notice `nag_live_dropout_paused` / `nag_pod_dropout_gave_up`) and `playRequested()` opens it; `PlaylistManager.dropoutChanged()` refreshes the shown state/Wi-Fi lock. Fake-service test: `podcast/DropoutRecoveryTest`.
- Live same-place ends: `StreamDropout.verdict(..., seekable, repeats)`: End only if seekable or the 3rd cut at the same place (`SAME_END_TIMES`); `seenSeekable` read in look(). `StreamDropout.reopenAt`.
- StreamWifiLock: LOW_LATENCY needs screen on + activity in front (HIGH_PERF = LOW_LATENCY since API 34): documented; reconnect logic is the screen-off protection; network caching not raised.
- Whisper: checkpoints `WhisperProgress`/`WhisperCheckpoint` (`files/whisper-progress/<episode>.json`, written after each finished 5-min piece, same model+language only); native `whisper_subs_run(..., start_ms, ...)` / `NativeLab.transcribe(..., startMs, listener)` decodes and drops audio before start_ms. `WhisperStop.of(...)` decides Fail/Next/Retry/Hold; Hold = ran without foreground (or STOP_REASON_TIMEOUT) and stopped on attempt ≥ 1 with the app not in front → `WhisperQueue.held` (persisted), no job starts while the head is held, `WhisperJobs.followApp` (ProcessLifecycleOwner, registered by PodcastCenter.schedule) releases on each app start, held requests become manual (auto=false). UI `TranscribeUi.Queued(waitsForApp)`. Channel `nagmedar_whisper` renamed at app start and once per process (createNotificationChannel updates the name).
